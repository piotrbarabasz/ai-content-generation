# D063 — Social / Standard video plan foundation

D063 introduces an optional, versioned planning object before the existing script
and media workflow. The initial product deliberately supports two profiles so the
outline, narration estimate and visual pacing have clear editorial expectations.
It does not offer arbitrary durations or platform presets.

## Format profiles

| Format | Allowed duration | Default | Preferred visual beat | Soft visual range |
| --- | ---: | ---: | ---: | ---: |
| Social | 30–60 seconds | 45 seconds | 6 seconds | 4–8 seconds |
| Standard | 540–660 seconds (9–11 minutes) | 600 seconds | 10 seconds | 8–12 seconds |

Social plans use four to eight flat beats, beginning with an opening and containing
at least one development beat. Each group has one planned section. Standard plans
use a cold open, introduction, five to seven chapter groups and a conclusion. A
chapter can contain multiple sections. These remain high level; neither format
changes sentence-safe scene segmentation or media timing.

## Domain and budgets

`VideoPlanRevision` is an immutable revision with project, language, format, target
duration, topic, working title, proposed film brief/style, nested groups and an
optional parent revision ID. `VideoPlanGroup` and `PlannedSection` are frozen values;
input sequences are copied to tuples. IDs are generated by the application.

Durations use deterministic integer-second largest-remainder allocation from
semantic positive integer weights. Group budgets sum exactly to the plan target;
section budgets sum exactly to each group. The planner estimates narration at
2.2 words per second (about 132 words per minute). This is one documented planning
baseline, not measured TTS duration. Scene counts divide section seconds by the
format's preferred visual-beat target and round to a whole editorial count. Measured
audio continues to determine actual duration downstream.

Generated semantic JSON has a dedicated strict schema with `additionalProperties`
disabled at each object. The model supplies titles, roles, purposes and positive
weights, not final arithmetic budgets or trusted IDs. The application validates
the structure and allocates all IDs and budgets before retention. Retained plan
payloads use version 1 and strict parsing.

## Persistence and visual context

Plan revisions and `video_plan_selection` events use the existing immutable local
artifact store and project artifact index. Each JSON payload is canonical and
checksum-verified on read. Project ownership is checked. Selection history is a
linear compare-and-select chain; a failed selection write leaves its prior head
active. The `project.sqlite` schema remains version 1 and has no migration.

The plan's film brief and visual style are suggestions. “Apply visual context” is
an explicit action that creates child `PromptContextRevision` values in the existing
`ProjectVisualPrompts` store. Visual prompt generation continues to resolve those
canonical context revisions; plan payload text is not substituted for prompt
context. Reapplying explicitly creates new history revisions rather than silently
changing existing context.

## Compatibility and deferred work

The Plan tab is optional. Existing projects without plans still open with an empty
plan view, and script editing, voice, scenes, visuals, timeline, export and the
automatic workflow do not require a plan. D063 does not change measured TTS timing,
image generation, render behavior, or `AutomaticWorkflow`.

D064 will connect a selected plan to script generation, including long-form
chapter-aware generation and the handoff from planned sections into the existing
script revision model. Sentence-safe scene planning and pacing changes remain
downstream work. The full editor redesign is also deferred.
